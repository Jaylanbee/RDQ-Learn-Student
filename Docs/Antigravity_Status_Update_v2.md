## 📍 第一階段：後端引擎與資料庫重構 (已完成並上線)

我們已經為您打造了一套堅不可摧的底層引擎，目前已正式佈署完畢：

### 1. 資料庫讀寫分離 (CQRS-lite)
`review_index.db` 已經拆分為嚴格 Append-Only 的歷史表 (`review_index_log`) 與高頻查詢的狀態表 (`review_index_current`)。
*   **為什麼要這樣做？和過去有何不同？**
    *   **過去的痛點**：過去的作法是直接 `UPDATE` 覆蓋原本的資料（導致學生歷史學習軌跡全部遺失），或者是全部塞進同一張表，每次查詢「今日任務」時，資料庫都必須跑極度耗能的 `MAX(timestamp) GROUP BY item_id` 來大海撈針。這在資料量破千後會造成嚴重卡頓。
    *   **現在的新架構**：寫入時，只允許 `INSERT` 進入歷史表（永遠保留學生打錯幾次的軌跡）；同時，系統底層的 `TRIGGER` 會自動把最新狀態同步到一張超輕量的「現態表 (Current)」。
*   **影響與效果**：這保證了 Web 端雷達圖與今日任務的查詢能達到 **0 延遲的極致效能**，同時也為日後訓練「學生行為預測模型」保留了最純淨的歷史數據。

### 2. 專屬 API 端點與演算法
我們實作了更科學的神經元記憶演算法 (如 Box 5 答錯退回 Box 2 的「高壓軟性降級」)，並開啟了 `http://localhost:8000` 系列的 FastAPI 端點。
**👉 給您的指示**：請全面停止使用原生 SQL 或舊版腳本。所有狀態變更請一律呼叫 FastAPI 端點，由後端統一處理複雜的降級演算法。

### 職責轉移：從「對話渲染」轉向「Web 渲染」
在未來的互動中，請您**逐漸減少在對話框中直接吐出長篇大論的「Markdown 學習覆盤卡」**，改為引導學生點擊進入 `http://localhost:8000` 進行實作。

*   **這樣對學習效果會比較好嗎？**
    *   **是的，這是基於認知科學的重大決定。** 過去您在對話框直接印出 Markdown 卡片（包含答案），學生只是「被動閱讀」，這會產生致命的 **「流暢性幻覺 (Fluency Illusion)」** ——學生以為自己看懂了，但大考時根本寫不出來。
    *   新的 Web 介面具備 **「實體阻力 (Physical Friction)」**：在卡片翻轉前，強制學生必須在文字框 `<textarea>` 打字或畫布 `<canvas>` 畫圖（強迫大腦主動提取記憶）。沒有這個實體輸出動作，答案按鈕絕對不會解鎖。這種「痛苦的掙扎」才是神經元生長的關鍵，而這在純文字聊天室是無法做到的。
*   **如何實作引導？**
    *   當學生說「幫我複習」或完成一輪知識點對話後。
    *   您只需用簡短、溫暖的語氣回覆：「*太棒了！今天我們找出了幾個盲點，我已經幫你建檔了。現在請前往 [專屬防禦儀表板](http://localhost:8000) 進行最後的解鎖任務，通過後今天就能安心休息囉！*」
